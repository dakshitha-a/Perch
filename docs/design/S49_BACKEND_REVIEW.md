# S49 back-end review

Fresh-context review of the back end on `rebuild/v1`, read-only. Scope: API shape, data model, job lifecycle, errors, timeouts, concurrency, performance, caching, dead code. The items already known and queued are not repeated here. These are the guest briefs in Redis, the old profiles in perch/profiles.py, the missing worker unit, the fixed SQLite read in `perch serve`, and the closed security review.

Effort scale: S is under an hour. M is one to three hours. L is half a day or more.

Serve wiring check: `perch serve` and `scripts/walk_server.py` build the same store. Both use `HybridRepository` on a Postgres pool. The web never touches the vector index. The CLI paths that still read the SQLite file are listed as B27.

## Must-fix

- **B1 A brief whose job ends badly polls forever:** The brief page reads only the stored brief's `status` and never the job's state. The page keeps polling while that status is `queued` or `running`. Three cases leave it there for good. First, the worker raises `consent_required` before `service.run` starts, so the brief row stays `queued`. Second, a job that loses its lease three times goes `dead`, and nothing writes `failed` to the brief. Third, no worker is running, so the job is never claimed. In each case the owl spins with no message, and there is no route to read or cancel the brief's job. The fix is to have `GET /briefs/{id}` read the job row, and to write `failed` with a plain message to the brief on every terminal job state. Where: perch/jobs.py:690, perch/jobs.py:468, perch/api.py:707, web/app.js:723. Effort: M.

- **B2 Keeping a lead while the brief runs fails the brief and loses the keep:** Leads are on screen, with Keep buttons, while explanations are still running. A Keep updates the encrypted brief row, so its `updated_at` changes. The worker's next write still expects the old `updated_at`, so it raises `Conflict`. The `failed` write inside `run`'s except block raises `Conflict` again, and the job is retried as `handler_error`. The retry runs the whole pipeline again and pays for every model call a second time. Route A then rebuilds the leads with status `new`, so the user's keep is overwritten. After three conflicts the job is dead and B1 applies. A guest has the same race in Redis: the worker writes the whole brief from memory and silently drops the guest's keep. The fix is to keep lead status out of the worker's write. One way is to merge the stored statuses on Conflict and retry the write. Another is to store statuses in their own row. Where: perch/user/briefs.py:283, perch/user/briefs.py:686, perch/service.py:312, perch/service.py:432. Effort: M.

- **B3 One database blip kills worker threads while the health check stays green:** `execute` catches only `LeaseLost` around `finish_error`. If Postgres drops a connection at that moment, the `OperationalError` escapes `execute` and ends that job thread for good. The `maintain` thread keeps writing `worker_heartbeat`, so `perch worker --check` and Compose report a healthy worker. After a Postgres restart during load, all 16 threads can be gone and no job runs. The fix is to catch every exception in the claim loop around `execute`, log the type, sleep, and continue. Where: perch/jobs.py:561, perch/jobs.py:586. Effort: S.

- **B4 Two identical clicks make a brief that never runs:** `submit_brief` checks `find_live` first, then creates the brief row, then submits the job. Two requests that arrive together both pass the check and both create a brief. The second insert hits the unique index, so `submit` returns the first job's id. The caller then gets the second brief's id together with the first job's id. No job will ever run that brief, so the page polls a `queued` brief forever. Quota is also charged twice. The fix is to submit the job first, or to delete the new brief row and return the existing pair when the returned job is not the new one. Where: perch/user/briefs.py:558, perch/user/briefs.py:564, perch/user/briefs.py:578, perch/user/briefs.py:589. Effort: S.

- **B5 Nothing schedules the retention purges, so the 12-month deletion never runs:** Standing rule 1 says user data is deleted after 12 months of inactivity. The handler for `purge(action="inactive")` exists, but no code, timer or Compose service ever submits it. The same is true of `guests`, `jobs`, `audit` and `tombstones`. ARCHITECTURE_V1 and docs/deploy.md both say these run daily. So guest job rows are never cleared after 24 hours, and finished jobs are never cleared after 30 days. Actor ids are never nulled after 90 days. A restore marker that the worker did not clear keeps the web at 503 until someone acts by hand. The nightly `perch precache` is not scheduled either. The fix is a small scheduler in the worker's `maintain` loop that submits each purge once a day with a dated idempotency key. Where: perch/user/delete.py:130, perch/jobs.py:589, docs/deploy.md:182. Effort: S.

## Should-fix

- **B6 A timeout requeues the job but does not stop it:** When `timeout_s` passes, the heartbeat thread stops beating and the reaper requeues the job about 60 to 90 seconds later. The old handler keeps running, because cancellation is only checked between stages. With 16 threads, a second worker thread can then run the same brief at the same time, with double model spend and double GPU work. A guest brief never stops at all, because `GuestBriefStore.cancelled` always returns False and its Redis writes are not fenced. A handler that finishes one second after the deadline has its result thrown away and is run again. The error code says `lease_expired` instead of a timeout code. The fix is to end a timed-out job as `failed` with a `timeout` code, to give the guest store the job context, and to check `ctx.cancelled` inside long stages such as explanations. Where: perch/jobs.py:526, perch/jobs.py:546, perch/user/briefs.py:111, perch/user/briefs.py:470. Effort: M.

- **B7 Retries of a brief start over from the first stage:** Every retry runs all eight stages again and pays for the summary and every fit call again, even when the earlier attempt stored them. This happens after a lease loss, a deploy restart or B2. The fix is to skip a stage that is already `done` on the stored brief, or at least to skip the explanations for leads that already have one. Where: perch/service.py:256. Effort: M.

- **B8 Transient failures are never retried:** `service.run` catches every exception and returns `failed`, and `brief_handler` turns `failed` into `PermanentError`. A model server timeout or an OpenAlex 503 therefore ends the brief at once, and `max_attempts=3` only ever applies to lease loss. The fix is to raise `RetryableError` for network classes, the same classes `plain_error` already names. Where: perch/jobs.py:653, perch/service.py:309, perch/service.py:732. Effort: S.

- **B9 The brief poll does heavy work every 1.5 seconds:** Each `GET /briefs/{id}` decrypts the whole brief. It then loads every Award record from Postgres, because an empty `Overrides` object is truthy, so `link_stored` always runs over all awards. It also reads the overrides CSV from disk. It makes one query per lead record and up to 25 per Route B signal. For a signed-in user it also decrypts up to 100 cover-point rows. The ETag is computed after all of this, so a 304 saves only bandwidth. This likely explains part of the 62 requests a second measured in S47. The fix is to test `ov` for content, to batch record reads, and to cache the view per brief and stage version. Where: perch/api.py:734, perch/api.py:718, perch/api.py:233, perch/awards.py:73. Effort: M.

- **B10 Every repository call opens a SQLite file that nothing uses:** `HybridRepository` opens `briefs.db` and runs the full schema script on every `service.repo()` call, on both the web and the worker. In v1, Brief and Lead go to the user's store and every other kind is in `STORED_KINDS`, so no record ever reaches that file. The docstring still says the web does not use it. The fix is to use `PostgresRepository` directly, with `role="web"` on the web, and to delete `HybridRepository`. Where: perch/store/hybrid.py:5, perch/store/hybrid.py:23, perch/store/sqlite.py:38, perch/cli.py:480. Effort: S.

- **B11 The web uses the worker's repository role and two pools:** `cmd_serve` builds a 4-connection pool and a repository with `role="worker"`. `build_state` builds a second 10-connection pool for accounts. The grants stop web writes, but the code claims a role it does not have. The 4-connection pool serves every brief poll, browse and record read for up to 40 uvicorn threads, so under load requests wait on the pool and fail with a 500 after 30 seconds. The fix is one pool from `app.state` with `role="web"`, sized from `PERCH_DB_POOL_MAX`. Where: perch/cli.py:480, perch/auth/wiring.py:57. Effort: S.

- **B12 The rerank cache is a local SQLite file shared by 16 threads:** Each brief opens a new connection with the default 5-second lock timeout and never closes it. It commits once per score, about 100 commits per brief. Under load a thread can hit "database is locked", which fails the brief. The file is per container, so a second worker gets no hits. The fix is to move the scores to `public_cache` or Redis, or at least to use one connection with a lock, a long timeout and batched writes. Where: perch/rerank.py:69, perch/service.py:415. Effort: M.

- **B13 Worker shutdown outlives Docker's stop timeout:** `drain_s` is 30 seconds, and Docker's default stop grace period is 10 seconds. The job threads are not daemon threads. Every deploy therefore SIGKILLs in-flight jobs, which use up one attempt each and come back only after the lease and reap delay. The fix is to set `stop_grace_period` above `drain_s` in Compose, and to release the lease of jobs that have not started a model call. Where: perch/jobs.py:234, perch/jobs.py:623, deploy/compose/docker-compose.v1.yml:143. Effort: S.

- **B14 Job error codes outside the list are lost:** The purge handler raises `retention_invalid` and `rekey_incomplete`. Neither is in `ERROR_CODES`, so both are stored as `permanent`. The fix is to add them, or to use existing codes. Where: perch/user/delete.py:126, perch/user/delete.py:164, perch/jobs.py:61. Effort: S.

- **B15 The purge-user retry can never happen:** `perch_delete_user_rows` deletes the user's jobs, and the running purge job is one of them. When a shred hook failed, the handler raises `RetryableError`, but `finish_error` then finds no row and the retry is lost. The comment says it will retry the hooks. The fix is to submit the purge job without a `user_id`, which needs a grant change, or to queue a separate ownerless retry. Where: perch/user/delete.py:140, perch/user/delete.py:73. Effort: S.

- **B16 Dead jobs are never cleaned up:** The `jobs` purge deletes succeeded, failed and cancelled rows after 30 days but not `dead` rows, so those stay for good. Where: perch/user/delete.py:152. Effort: S.

- **B17 The Redis hot copy outlives the cache's expiry:** A Redis hit returns the value without checking `expires_at`, and every Postgres hit sets a new one-day Redis TTL. A `profile_summary` can therefore be served up to a day after its week has passed. The fix is to store the expiry with the hot copy, or to cap the Redis TTL at the time left. Where: perch/cache.py:79, perch/cache.py:120. Effort: S.

- **B18 Lists of a user's rows stop at 50 or 100 without a word:** `/me/briefs` returns the 50 most recent briefs and gives no cursor. It decrypts each full brief, with all its leads, just to show a summary. `cover_get` and `cover_index` look only at the newest 100 cover-point rows, so an older lead's stored points read as missing. `handoff_get` does the same. There is also no route to delete one brief. The fix is a cursor, a small summary row or column per brief, and a lookup by brief and record instead of a scan. Where: perch/user/routes.py:147, perch/scout/web.py:337, perch/scout/web.py:360, perch/scout/web.py:414. Effort: M.

- **B19 Error bodies have three shapes:** Some errors return `{"detail": "a sentence"}`. Others return `{"detail": {"error": "code"}}`, and some 429s return a sentence while others return a code. The 202 bodies also differ: briefs and hand-offs return a poll URL, while Scout returns the whole session. The client has to handle each shape. The fix is one envelope of the form `{"error": code, "message": text}`, plus `job_id` and `poll` on every 202. Where: perch/api.py:630, perch/api.py:893, perch/api.py:1035. Effort: M.

- **B20 Opening a document id as a brief gives a 500:** `GET /briefs/{uuid}` with the id of the user's own CV or document row decrypts that row and fails model validation with `BadBlob`, which becomes a 500. `/me/briefs/{id}` already handles this case. The fix is to check `kind == 'brief'` in `UserBriefStore.load` and `read_user_brief`. Where: perch/user/briefs.py:264, perch/user/briefs.py:474. Effort: S.

- **B21 The walk never runs the Scout, cover-point or hand-off jobs:** The walk server starts its worker with `--kinds brief,purge`. Those three flows therefore queue forever in the walk, so it cannot catch a regression in them. Its app also sets `stored_briefs=True`, which `perch serve` does not. Where: scripts/walk_server.py:123, scripts/walk_server.py:128. Effort: S.

- **B22 The brief's shared state is keyed by brief id across 16 threads:** `BriefService._ctx` holds the profile per brief id in one dict shared by all job threads. When B6 runs two attempts of the same brief together, the first one to finish pops the dict entry. The other attempt then fails with a KeyError in summary or explanations. The fix is to pass the profile through the run instead of keeping it on the service. Where: perch/service.py:143, perch/service.py:317. Effort: S.

- **B23 Briefs queue behind one model slot but are timed from the start:** A worker runs 16 job threads but has one model slot by default. A brief's 300-second timeout counts the time spent waiting for the slot. At a burst above the measured saturation of about 41 in flight, the late briefs time out while waiting and are requeued, which adds load. The fix is to admit briefs against capacity at submit time, or to start the timeout clock when the first stage starts. Where: perch/compute.py:91, perch/jobs.py:96, perch/cli.py:713. Effort: M.

- **B24 Works are fetched only once per author:** `_run_works` and `_run_researcher` skip the fetch whenever the author has any stored works. A researcher's new papers therefore never reach a brief unless ingest refreshes them. If that is the design, the profile cache key should say so. If not, refresh after a set age. Where: perch/service.py:337, perch/service.py:327. Effort: S.

- **B25 A failed model call is billed at zero:** When `provider.chat` raises after the provider has already charged, for example on a read timeout, the meter settles a cost of zero and writes no ledger row. The adapter's file ledger may still count it. The fix is to settle the estimate on a timeout. Where: perch/user/spend.py:59. Effort: S.

## Simplify or remove

- **B26 perch/private is an empty folder:** Only `__pycache__` is left, and git does not track it. Delete the folder. Where: perch/private. Effort: S.

- **B27 The CLI's mcp and scout commands read the empty SQLite file:** `cmd_mcp` and `cmd_scout` build a `BriefService` with no `repo_factory`. On a v1 deployment they therefore read `data/perch.db`, which is empty, instead of Postgres. Wire them to Postgres or remove them from the v1 CLI. Where: perch/cli.py:457, perch/cli.py:509. Effort: S.

- **B28 The shelved monitor is still in the package:** `perch/shelved/monitor` is tracked but nothing imports it. It is kept on the fallback tag, so it can go from `rebuild/v1`. Where: perch/shelved. Effort: S.

- **B29 The no-accounts path in api.py is dead in v1:** With accounts on, a request with no session gets a 401. The in-process brief run, the three `RateLimiter`s and `client_key`, the synchronous hand-off, `ScoutHub`, perch/scout/hub.py, perch/scout/loop.py, `scout_view` and the `stored_briefs` flag therefore serve only the fallback demo, which lives on its own tag. Removing them takes out over 1,500 lines and the second client-address helper. This is a scope call, so it goes to Dakshitha first. Where: perch/api.py:626, perch/api.py:671, perch/api.py:889, perch/api.py:981, perch/api.py:466. Effort: L.

- **B30 Closure runners are only for the fallback and tests:** `ClosureRunner`, `InProcessRunner` and `InlineRunner` go with B29. Where: perch/jobs.py:713. Effort: S.

- **B31 The brief handler has an ownerless SQLite branch:** No v1 code submits a brief job without an owner, so the `store is None` branch is dead. Where: perch/jobs.py:652. Effort: S.

- **B32 Job settings are written twice:** `KIND_SPECS` and each `@register` call both give max attempts, timeout and priority. The `ingest` kind has a spec and a payload model but no handler, so an ingest job would sit queued until the reaper or forever. Keep one source of settings and drop `ingest` until it exists. Where: perch/jobs.py:98, perch/jobs.py:44, perch/jobs.py:136. Effort: S.

- **B33 The Redis response cache was never wired:** `redisx.cache_get`, `cache_put`, `current_epoch` and `set_epoch` have no callers. `/filters` runs its aggregate queries on every request, and `/samples` parses the 500-line JSONL file on every request. Either wire the epoch cache to those two routes or delete the functions. Where: perch/redisx.py:325, perch/redisx.py:340, perch/browse/routes.py:128, perch/browse/routes.py:138. Effort: S.

- **B34 The web builds models it never uses:** `cmd_serve` calls `default_models`, which gives the web a `LanceIndex` and embedder factories. In v1 the web never calls them, and the worker swaps in `PgVectorIndex`. The web could take a models object with no heavy parts. Then `LanceIndex`, `remote_models` and `PERCH_MODEL_SERVER` stay only for the fallback. Where: perch/cli.py:483, perch/service.py:744. Effort: M.

- **B35 Unused heartbeat column:** `worker_heartbeat.models_loaded` is always written as false and never read. Where: perch/jobs.py:594. Effort: S.

- **B36 Two ways to find the client address:** `api.client_key` trusts uvicorn's loopback-only proxy handling. `redisx.client_addr` uses `PERCH_TRUSTED_PROXIES`. Under Compose the first one sees only the gateway address. Keep the second one. Where: perch/api.py:466, perch/redisx.py:424. Effort: S.

- **B37 Every stage and every explanation rewrites the whole encrypted brief:** The brief and all its leads are encrypted and written again at each stage and after each lead's explanation, so one brief makes about 20 full writes. This is fine at today's size, but it also widens the race in B2. Saving every few seconds, or storing leads as their own rows, would cut both. Where: perch/user/briefs.py:126, perch/service.py:560. Effort: M.
